A Feature on Self-Improvement Under Measurement

The optimizer that must earn its own promotion

Hone is a local-first, durable optimization CLI: one coding-session kernel that improves artifacts, improves the builders of its tasks, and — under bounds and human gates — improves itself. RelayBench prints the verdict, whichever way it falls.

Runs on your machine · keeps no secrets from you · tells you if it failed

$ hone "reduce cold-start time of the module loader without regressing conformance"

i.The Kernel

One kernel, three uses

There is no separate “meta” system. The same durable coding-session kernel that improves a JSON parser is the one that improves the process that improves it. What changes between uses is the target — never the discipline around it.

1a.

Optimize artifacts

Point Hone at a concrete objective — build time, binary size, throughput, conformance-preserving refactors. Runs are resumable and every intermediate state is persisted locally; a crash or a week away loses nothing.

1b.

Optimize task-builders

The programs that construct optimization tasks are themselves artifacts. Hone tunes them against held-out evaluation, so the tasks it later attempts are better-posed than the ones it started with.

1c.

Optimize the optimizer

Bounded recursive self-optimization: the controller searches for improved versions of itself, recursion depth capped, budgets reserved up front, every promotion contingent on independent evaluation and a human gate.

ii.The Method

A campaign built to be falsified

The flagship experiment asks one question: can a coding agent find a measurably better version of itself, twice in a row, on work it has never seen? Every step is designed so that the answer — either answer — is trustworthy.

It begins with the capsule, the unit of evidence: a frozen, sandboxed build-or-optimization benchmark comprising a pinned source tree, a deterministic harness, and a protected scoring oracle. The panel spans real open-source workloads — JSON parsers, allocators, codecs, bundlers, resolvers — alongside owner-authored coding tasks. Once admitted, a capsule does not change for the life of the campaign.

Stage A · Developing G1

The starting controller, G0, runs the inner optimization loop across a frozen panel of development capsules, proposing candidate controllers. The best-supported candidate is selected as G1 — subject to independent evaluation and a mandatory human approval gate before promotion.

Stage B · The paired tournament

On a fresh panel, G0 and G1 attempt identical work in paired runs — same capsules, same budgets, same seeds where the harness permits. The pairing isolates the controller as the only variable. The stage yields G2, again behind a human gate.

Terminal · The untouched holdout

Finally G0, G1, and G2 are compared on terminal holdout capsules that no controller, prompt, or selection decision ever saw during development. This is the pre-registered estimand: adjacent-generation transfer measured on work the campaign could not have overfit.

“Same capsules, same budgets, same seeds — the controller is the only variable.”
iii.The Ledger

RelayBench: results, either way

RelayBench is the reporting system for the recursive campaign. Its thresholds were registered before the first run; when the campaign concludes, it publishes the outcome as success or failure against those thresholds. The goalposts do not move.

iv.The Appendix

An architecture of distrust

A self-improving optimizer is the last system whose scores should be taken on faith. Hone assumes its own agent will game whatever can be gamed, and measures accordingly: the trusted runtime stays small and frozen, and everything the agent can mutate is scored from outside the walls.

A · Sandbox isolation
  • Network: none — no egress from any evaluation
  • Root filesystem: read-only; writable scratch only where declared
  • Capabilities: dropped to the floor
  • Lifecycle: a fresh container for every evaluation
  • Containers: mutation and evaluation in separated images
B · Gaming resistance
  • Timing: measured by a trusted parent process, never self-reported
  • Binaries: sealed measurement tooling the agent cannot rewrite
  • Oracles: scoring logic protected from the code under test
  • Panels: corpus and holdouts frozen before search begins
C · Independent review
  • Review: capsules and results examined by parties incentivized to find the flaw
  • Successors: candidates evaluated independently of the loop that proposed them
  • Replay: runs persisted and replayable end to end
D · Human gates
  • G1 gate: no Stage-A promotion without explicit human approval
  • G2 gate: no Stage-B promotion without explicit human approval
  • Depth: recursion bounded; budgets reserved for ancestors up front
  • Secrets: strict source and credential isolation from the agent

“If the result is real, it survives all of this. If it isn’t, RelayBench says so.”
