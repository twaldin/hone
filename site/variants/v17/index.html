00 / Overview Optimization CLI

State an objective. Hone finds a measurably better version — or tells you it didn’t.

Hone is a command-line tool that improves code by measurement. It edits a copy of your project, builds and tests each candidate in a sandbox, scores it with tooling the candidate cannot touch, and keeps whatever scores better. Every step is written to disk as it happens — a crash, a reboot, or a week away loses nothing.

Runs on
Your machine. No telemetry, no network during evaluation.
State
Durable. Every event persists; resume any time.

01Kernel

One engine, three targets

Hone has one engine: a durable coding session that proposes a change, measures it, and keeps the result. There is no separate “meta” system. The parts of Hone that improve Hone are the same engine pointed at different code.

1.1

Your code

Name an objective — build time, binary size, throughput, a refactor that must not change behavior. Hone proposes candidates and measures each one against your checks. It lands nothing on its own: hone diff shows the change, hone apply --best puts it on a branch.

1.2

Its task-builders

The programs that write Hone’s practice tasks are code too. Hone tunes them against held-back scoring runs, so the next round of tasks is better posed than the last one.

1.3

Itself

The controller that runs the search can search for a better controller. Depth is capped. Budgets are reserved before recursion starts. No successor is promoted without an independent evaluation and a person’s recorded approval.

02One run

One run, end to end

What happens between hone "<objective>" and hone apply. The event names below are the real ones from the run log. The numbers are illustrative — the product has published no results.

run.started

The objective becomes a contract

Hone snapshots your project and opens a durable session. The objective is turned into a scored contract: what to improve, what must not regress, and how both are measured. hone status shows it at any point.

episode.started

Each episode proposes one candidate

An episode is one attempt: an edit, a build, a test run inside a fresh sandbox. The candidate never reports its own numbers — a separate trusted process does the timing and the scoring.

incumbent.new

Winning once is not enough

The incumbent is the best version found so far. A candidate that beats it is re-measured before it takes the title; the shaded band in Fig. 2.1 is that repeat-measurement spread. One lucky run does not get promoted.

budget.snapshot

You set the ceiling

Budgets are stated up front — --budget-usd 20 — and reserved before the search starts. Hone accounts for every evaluation against the ceiling and stops when it is spent, keeping the best incumbent.

run.finished

You decide what lands

hone best names the winner, hone diff --stat summarizes the change, hone apply --best lands it on a branch. A stopped or crashed run continues from its own log with hone resume.

03Campaign

The campaign and its gates

The first public test of Hone asks one falsifiable question: can the controller find a better version of itself, twice in a row, on work it has never seen? G0 is the controller Hone ships with; G1 and G2 are its would-be successors. Three words carry the design.

Capsule
A frozen benchmark: pinned source, a fixed harness, a scoring script the candidate cannot modify. Real open-source workloads — parsers, allocators, codecs, bundlers, resolvers — plus owner-written tasks. Once admitted, a capsule never changes.
Panel
A fixed set of capsules assigned to one stage, frozen before the search begins. Development, tournament, and holdout panels do not overlap.
Gate
A stop. A person reviews the evidence and signs, or nothing moves. The campaign has two, and neither can be skipped by anything the optimizer does.
3.1

Stage A · G0 → G1

G0 runs the search across the development panel, proposing candidate controllers. The best-supported one is put to the first gate.

Gate 1 · human
3.2

Stage B · G0 vs G1 → G2

On a fresh panel, G0 and G1 attempt identical work — same capsules, same budgets, same seeds where the harness permits. The controller is the only variable. The stage yields G2.

Gate 2 · human
3.3

Terminal · G0 G1 G2

All three generations run the holdout panel — capsules that no controller, prompt, or selection decision touched during development. What transfers there was learned, not memorized.

What the reviewer at a gate actually sees

  • Per-capsule paired scores — not an average that hides the losses.
  • The budget ledger — what was reserved, what was spent, by whom.
  • The full diff of the candidate controller against its parent.
  • The replay command that regenerates every number from the run log.

Approval is recorded as a receipt tied to that exact evidence. A rejected candidate stays put; the campaign continues with the incumbent.

04RelayBench

RelayBench — the report, either way

RelayBench is the campaign’s report. Its thresholds were registered before the first run. When the campaign ends, it publishes the outcome against them — pass or fail, in the same document, at the same thresholds. Nothing below is a result yet.

What it will publish

  1. Learning curves — score against budget, per capsule and across generations.
  2. Paired deltas — G1 − G0 and G2 − G1 on each capsule, with confidence intervals.
  3. Sign consistency — on how many capsules the later generation wins at all. A mean carried by two outliers is reported as exactly that.
  4. The headline comparison — on the holdout panel, weighted 50/50 between owner tasks and pinned open source, so neither family dominates.
  5. The integrity audit — the capsule pool was spent as registered: no holdout contact, no re-rolled panels, no post-hoc exclusions.

Why replayability matters

Every published number ships with the run records that produced it. A Hone run is an event log; replaying the log regenerates the number on your machine, from run.started to run.finished. A result that cannot be replayed is an anecdote.

05Trust

Measurement lives outside the walls

A self-improving optimizer is the last system whose scores should be taken on faith. Hone assumes the candidate will lean on any seam it can reach — so every measured surface is kept out of reach.

5.1Sandbox isolation

Networknone — no egress from any evaluation
Root filesystemread-only; writable scratch only where declared
Privilegesno extra privileges; capabilities dropped
Lifecyclea fresh container for every evaluation
Imagesediting and evaluation run in separate containers

5.2Gaming resistance

Timingmeasured by a trusted parent process, never self-reported
Binariessealed measurement tooling the candidate cannot rewrite
Scoringoracles protected from the code under test
Panelscorpus and holdouts frozen before the search begins

5.3Independent review

Reviewcapsules and results examined by people whose job is to find the seam
Successorscandidates evaluated independently of the loop that proposed them
Replayruns persisted and replayable end to end

5.4Human gates

Gate 1no Stage-A promotion without a recorded human approval
Gate 2no Stage-B promotion without a recorded human approval
Depthrecursion bounded; ancestor budgets reserved up front
Secretsstrict source and credential isolation from the candidate

If the improvement is real, it survives all of this. If it isn’t, RelayBench says so — same report, same thresholds.
