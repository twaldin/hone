What this change does: When a candidate's worker process has exited but a detached child it started still holds the result pipe, the grader now keeps the worker's real exit code and whatever result frame it captured. Before, this case became "timed out, score 0". The head also adds a Docker regression test, updates the two source pins, keeps the fresh zero-call admission, smoke and full-suite proof, and points the active scripts and runner test at `runtime-rerun-11b`.

**The fix itself** (`pilot/verification.py:424-459`)
- The supervisor now checks whether the worker has exited before it checks the deadline. An exited worker's captured bytes go back to the caller with its real exit code. Only a worker still running at the deadline gets the "time limit, score 0" verdict.
- Outcomes now match the ruling:
  - A valid result frame scores normally, and a trusted candidate failure scores 0.
  - Exit with a nonzero code is `nonzero_exit`, unscored.
  - Exit 0 with no frame is `frame_failure`, unscored.
  - A candidate still running at the deadline scores 0.
- An escaped child cannot change the exit code. It can only corrupt the frame, which makes the case unscored. A candidate could already do that itself with `os._exit(0)`.
- The planner's expected answers never reach the worker, so a forged frame gains nothing over solving the task.
- Timing is unchanged. In the smoke run, escaped cases took about 10.33 s against the 15 s outer limit, about the same as the existing timeout case (10.347 s).

**Nice to have** (neither blocks launch)

1. **Rare edge at the exact deadline** (`pilot/verification.py:432-433`)
   - **What this is:** at the deadline, if the worker has exited, the supervisor returns the bytes it has read so far.
   - **Problem:** the worker might write its frame and exit in the few microseconds between the last read attempt and the exit check. Then the frame is still in the pipe and the result becomes unscored `frame_failure`; the old code gave score 0. This needs a CPU switch in that tiny window on the one-CPU container, plus a candidate finishing at exactly 10 s. I judge this negligible (inference); the slowest admission run took 0.243 s.
   - **Fix:** in that branch, read whatever is already waiting (zero wait, capped at the wire limit) before returning. About 4 lines, but it would need new pins and a new admission, so only bundle it into a later grader change.
   - **If we skip it:** at worst one cell stops as an infrastructure failure. It can never produce a wrong score.
